# ۰۹ — باید و نباید

قواعدی که با هزینه یاد گرفته شدند، و تله‌هایی که اگر ندانی وقت می‌گیرند.

---

# نصب در ایران

مهم‌ترین بخش این صفحه. اگر این را ندانی، اولین build وسط راه می‌شکند و سیستم
اصلاً بالا نمی‌آید.

## مسئله

سه چیز جدا:

| چه چیزی | از کجا | وضعیت |
| :--- | :--- | :--- |
| بیشتر پکیج‌ها | `cache.nixos.org` | معمولاً در دسترس |
| `niri`، `noctalia` | cachix | معمولاً در دسترس |
| `nvim-dap` و خانواده | **`codeberg.org`** | ✖ در دسترس نیست |

پکیج‌های `codeberg` مشکل‌سازند چون `nix` قبل از build باید سورس را بیاورد، و
وقتی نتواند، **کل build شکست می‌خورد** — نه فقط آن پلاگین.

## راه‌حل: اول کامنت، بعد پروکسی، بعد برگردان

### مرحله ۱ — کامنت کن تا سیستم بالا بیاید

در `modules/home/dev/nvim/default.nix` این پنج خط:

```nix
# nvim-dap
# nvim-dap-ui
# nvim-dap-virtual-text
# nvim-dap-python
# one-small-step-for-vimkind
```

و در `lua/dap.lua` نگران نباش — با `pcall` محافظت شده، پس نبودن پلاگین
باعث خطا نمی‌شود.

### مرحله ۲ — بساز

```sh
sudo nixos-rebuild switch --flake .#nixos
```

حالا یک سیستم کارآمد داری، فقط بدون دیباگر.

### مرحله ۳ — پروکسی برای nix-daemon

```sh
nix_proxy 1819
```

**چرا این و نه `export HTTP_PROXY`:** دانلودها را `nix-daemon` انجام می‌دهد،
که یک سرویس systemd جداست. متغیرهای محیطی شل تو **هیچ اثری روی آن ندارند**.

این تابع یک drop-in در `/run/systemd/system/nix-daemon.service.d/` می‌نویسد
و سرویس را ریستارت می‌کند.

### مرحله ۴ — کامنت‌ها را بردار و دوباره بساز

```sh
sw
nix_proxy off
```

از این به بعد آن پلاگین‌ها **در store هستند** و هر build بعدی بدون پروکسی
کار می‌کند. فقط وقتی `nix flake update` نسخه‌شان را عوض کند دوباره لازم
می‌شود.

## چند نکته‌ی دیگر برای اتصال ضعیف

**`aria2` برای دانلود دستی** — چندنخی و قابل ادامه.

**`dev` هرچه یک بار وارد شوی را GC-root می‌کند.** یعنی محیطی که نیم ساعت
دانلود شده، با `nix store gc` پاک نمی‌شود. → [۰۳](03-dev.md)

**`nix-index-database` از پیش ساخته می‌آید** — بدون آن باید ده دقیقه CPU
خرج ساخت ایندکس کنی.

**`px` برای برنامه‌هایی که پروکسی را نادیده می‌گیرند:**

```sh
px curl https://example.com
```

**`proxy_on` فقط روی همین شل اثر دارد** — تب دیگر تحت تأثیر نیست.

# قواعد کلی

## هرگز کلید API در کانفیگ نگذار

`/nix/store` برای **همه‌ی کاربران خواندنی** است. یک کلید آنجا یعنی یک کلید
لو رفته، و چون در گیت هم هست، تاریخچه هم داردش.

راه درست: `agenix` برای رازهای سیستم، و برای AI داشبورد `9router` که
کلیدها را بیرون از این مخزن نگه می‌دارد. → [۰۷](07-ai.md)

## فهرست دوم نساز

**درس تکرارشونده‌ی این پروژه.** هرجا دو جا باید هم‌زمان به‌روز شوند، یکی
فراموش می‌شود.

نمونه‌های واقعی:

- منوی `dev` از `devShellsMeta` می‌خواند، نه از فهرستی در launcher
- تکمیل خودکار `dev` مستقیم `shells/*/` را می‌خواند
- فهرست مدل‌های AI از `/v1/models` می‌آید، نه از جدولی در `ai.lua`
- جدول‌های `keys.md` از سورس تولید می‌شوند

اگر مجبوری فهرست دوم بسازی، **تولیدش کن** نه اینکه بنویسی‌اش.

## قبل از کامیت، `nix-check`

```sh
dev nix && nix-check
```

`statix` + `deadnix` + `nix flake check`. سه ثانیه وقت می‌گیرد و جلوی
کامیتی را می‌گیرد که نمی‌سازد.

## `tst` قبل از `sw` وقتی مطمئن نیستی

`nh os test` اعمال می‌کند ولی برای بوت بعدی ثبت نمی‌کند. اگر سیستم خراب شد،
ریست کافی است.

## قبل از افزودن ابزار، پکیجش را باز کن

```sh
pip download hermes-agent --no-deps -d /tmp/h && unzip -q /tmp/h/*.whl -d /tmp/h/w
```

نصب کردن و بعد فهمیدن اینکه چه می‌خواهد، ترتیب اشتباهی است.

# تله‌ها

## دستور اشتباه، جستجوی پکیج راه نمی‌اندازد

```
$ caler
fish: Unknown command: caler
```

اگر روزی دیدی مکث می‌کند و می‌نویسد `caler: command not found` (با این
شکل)، یعنی یک handler برگشته. شرح کامل در [۱۰ تصمیم‌ها](10-decisions.md).

## `hms` وجود ندارد

home-manager اینجا یک **ماژول NixOS** است، پس flake خروجی
`homeConfigurations` ندارد و `nh home switch` شکست می‌خورد. `sw` هر دو را
با هم می‌سازد.

## `dev -w` نه `nix eval`

برای دیدن محتویات یک شل از `dev -w` استفاده کن — ۴۳ میلی‌ثانیه در برابر یک
ارزیابی کامل flake.

## محیط‌های `dev` با `nix store gc` پاک نمی‌شوند

عمدی است. برای آزاد کردن فضا:

```sh
rm ~/.local/share/dev-roots/<name>-profile
nix store gc
```

## `box` در برابر بدافزار نیست

`bwrap` کرنل را با میزبان شریک است. ابزار درست برای «کدی که نخوانده‌ام» و
«جلوی کثیف‌کاری در home». برای بدافزار واقعی `box vm`. → [۰۸](08-sandbox.md)

# چرا این تنظیمات سیستمی

## حافظه — ZRAM با `swappiness = 180`

عدد ۱۸۰ در یک سیستم معمولی دیوانگی است (پیش‌فرض ۶۰). اینجا درست است چون swap
روی **ZRAM** است، یعنی در رم و فشرده — نه روی دیسک.

وقتی swap سریع‌تر از خواندن دوباره از دیسک است، منطق برعکس می‌شود:
swap کردن **بهتر** از دور انداختن کش است.

```
zramSwap.memoryPercent = 100
vm.swappiness            = 180
vm.page-cluster          = 0     خواندن دسته ای بی معناست وقتی در رم است
vm.vfs_cache_pressure    = 50    کش inode را بیشتر نگه دار
```

## دیسک — `dirty_ratio = 10`

پیش‌فرض کرنل اجازه می‌دهد حجم زیادی داده در رم منتظر نوشتن بماند. روی NVMe
این یعنی هر از گاهی یک وقفه‌ی محسوس وقتی همه با هم فلاش می‌شوند.

```
vm.dirty_background_ratio = 5     زودتر شروع کن به نوشتن
vm.dirty_ratio            = 10    سقف کمتر
```

نتیجه: نوشتن مداوم و کوچک به‌جای وقفه‌های بزرگ. دسکتاپ زیر بار روان می‌ماند.

## امنیت — چه چیزی روشن است

```
فایروال          هیچ پورتی باز نیست
sudo-rs          پیاده سازی امن حافظه
AppArmor         سندباکس کرنل
firejail         سندباکس برنامه
OpenSnitch       فایروال سطح برنامه
USBGuard         حفاظت USB
/tmp             هر بوت پاک می شود
```

sysctlهای مهم:

```
kernel.kptr_restrict      آدرس کرنل را لو نده
kernel.dmesg_restrict     dmesg فقط برای root
kernel.sysrq              محدود
dev.tty.legacy_tiocsti    ۰ — جلوی تزریق کلید
```

`legacy_tiocsti` صریحاً پین شده چون `box` در حالت تعاملی `--new-session` را
حذف می‌کند و به همین sysctl تکیه دارد. → [۰۸](08-sandbox.md)

## شبکه — BBR و DNS رمزگذاری‌شده

`BBR` الگوریتم کنترل ازدحام گوگل است. روی اتصال با تأخیر بالا و بسته‌ی
گم‌شده — یعنی دقیقاً شرایط اینجا — محسوس بهتر از `cubic` پیش‌فرض کار می‌کند.

`dnscrypt-proxy` جلوی دیدن و دستکاری درخواست‌های DNS را می‌گیرد.
